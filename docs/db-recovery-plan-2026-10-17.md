# 과거 판례 DB 누락 복구와 게시 전 대조 계획

> 이 문서의 수치와 범위는 당시 감사 기록입니다. 현재 범위와 후속 검증은 [법원·헌재 전용 전환 결과](court-only-cleanup-2026-10-18.md)를 따릅니다. 법원·헌재 판례는 국세 출처·특허 주제로 제외하지 않습니다.


> 최신 단계: Cloudflare master를 내려받아 신규 29,269행과 raw 보존 overlay를 반영한 로컬 사본 및 검토용 20261018 세대를 검증했다. 기존 master 전체 export·증분 health gate는 실패해 운영 게시를 차단했다. [정정 사전·master 통합 보고서](C:/projects/bupgogae/docs/known-error-serving-integration-2026-10-18.md)를 따른다.

2026-10-18 후속 단계에서 공단의 남은 29,081행 전부에 최종 판단을 남겼다.
이번 모집단 28,773 ID와 이전 보류 2 ID를 추가한 최종 로컬 후보는
161,719키·163,478개 레코드 연결이다. 184행은 기존 연결로 확인했고 124행은
보류했다. 정정 dictionary·원문 해시·재개 일지와 독립 검증·실제 Store ZIP 결과는
[최종 원출처 대조 보고서](C:/projects/bupgogae/docs/full-worker-source-recovery-2026-10-17.md)에 있다.
운영 게시·master 교체는 하지 않았으며 게시 차단을 유지한다. 아래 계획과 수치는

## 추가 보완 범위와 현재 상태

사용자 확인에 따라 국세 자료와 특허 사건은 **이번 정규화 보완·복구에서만**
제외한다. 정기 수집의 영구 필터, 기존 DB 삭제, 확장 탐지 범위 변경은 적용하지 않는다.
추가 발견 34건 중 국세법령정보시스템 33건이 범위 밖이며, 나머지 지방세 출처
ID 420836 한 건의 병합 사건번호를 보완했다. 제외된 국세 출처 33건을 해결했다고
보고하지 않는다.

420836은 원문 ID 1행과 사건번호 원문을 그대로 저장하면서 5개 조회 키를 모두
내보낸다. 이 보완은 SQLite schema나 공개 snapshot 형식을 변경하지 않는다.
지방세연구원 원문 표제에서 공통 부분과 각 `(병합)` 표식을 확인했다.
공통 연도·사건부호가 경합하거나 표식이 빠진 생략 번호는 계속 실패 처리한다.

기존 아래의 full-bootstrap 명령은 **모든 출처를 수집하는 기존 runner의 명령**이다.
이번 국세·특허 제외 복구에는 그대로 실행하지 않는다. 실제 복구 실행 전 별도
candidate 범위와 제외 목록을 journal하고 출처·공식 사건분류 근거와 건수를 보고해야 한다.
필터링 전 원천 totalCnt·전 페이지 검증은 유지하며, 제외를 통신 실패나 정상 0건과
섞지 않는다. 제목의 단어만으로 국세·특허를 추정해 제외하지 않는다.

이번 추가 검증에서는 운영 master·번들·공개 DB를 갱신하지 않았다.
검증 로그는 `audit/2026-10-17/merged-before.log`, `merged-after.log`,
`merged-python-all.log`, `merged-e2e/`에 보존한다. Python 신규 9개 포함 전체
111개와 실제 ZIP의 신규 병합 일괄 조회 E2E 1개가 통과했다. 앞선 전체 E2E의
cold 설치 60초 실패는 별도 미해결 항목이며 전체 릴리스 통과로 취급하지 않는다.

## 1단계 운영 상태 보존과 원인 구분

1. 운영 배포본, manifest, 해당 게시 실행의 commit SHA와 로그를 보존한다.
   이미 확보한 공개본과 실제 복구 시작 시점의 공개본은 별도 식별한다.
2. trusted state 경로에서 current/previous pointer, master DB, backlog를 읽기
   전용으로 확보한다. 라이브 SQLite는 파일 단순 복사 대신 SQLite backup을
   사용한다. 원본 해시·크기·generation·확보 시각을 기록한다.
3. 각 ID가 master에 없는지, master에는 있으나 export에서 빠졌는지 대조한다.
   사건번호는 같은 법원·날짜의 다른 원문과 충돌할 수 있으므로 ID를 우선한다.
4. baseline 검증 실패 시 기존 운영 자료를 덮지 않는다. previous generation도
   확인하고, 빈 DB 재구축은 기존 전체 레코드와의 차이를 별도로 보고한다.

산출물은 `audit/recovery-20261017/baseline/`에 둔다. 원천 XML과 DB는 공개
자료지만 state 파일과 실행 로그는 secret 검사를 거쳐 외부 공유한다.

## 2단계 격리 재수집

운영 master의 검증된 복사본을 `audit/recovery-20261017/candidate/master.db`에
둔다. 기존 backlog를 없애지 말고 이관한다. 후보 경로에는 운영 시스템을
연결하거나 운영 DB 파일을 심볼릭 링크로 연결하지 않는다.

기존 범위가 잘못된 0건으로 완료 처리됐으므로 현재 backlog만 재실행하는 것으로는
충분하지 않다. `--full-bootstrap`으로 1948-08-15부터 복구 실행일까지 전체
범위를 다시 journal한다. 현재 구현은 연 단위이며 2026-10-17 기준 79범위와
헌재 최대 400페이지다. 1948년 이전의 기존 레코드는 보존하지만 이 계획의
재수집 범위 밖이므로 전수 대조 완료라고 표시하지 않는다.

운영 backlog에 기존 `full_bootstrap` marker가 있으면 그대로 실행할 경우 pending만
재개하고 과거 완료 범위를 건너뛴다. **새 복구 candidate를 처음 준비할 때만**
원본 backlog를 별도 보존한 다음, 검증된 pending 항목 전체를 유지하면서 candidate의
mode를 `incremental`로 저장한다. 그러면 첫 `--full-bootstrap` 실행이 전체 계획과
기존 pending을 합쳐 새 journal을 만든다. 복구를 재개할 때 이 초기화를 반복하면
완료 구간을 매번 재수집하므로 수행하지 않는다. 이 단계도 운영 state에는 적용하지 않는다.

```powershell
.venv/Scripts/python.exe -c "import sys; sys.path.insert(0,'pipeline'); import crawler_runner as c; p='audit/recovery-20261017/candidate'; items, mode=c.load_failed_dates_state(p); c.save_failed_dates(p,items,mode=c.BACKLOG_MODE_INCREMENTAL,retain_empty=True)"
```

먼저 아래 명령으로 계획만 확인한다. 네트워크·수집·게시를 수행하지 않는다.

```powershell
.venv/Scripts/python.exe pipeline/crawler_runner.py --plan --full-bootstrap --data-dir audit/recovery-20261017/candidate
```

실수로 직접 게시하지 않도록 실제 수집은 아래와 같이 **해당 Python 프로세스에서만**
R2·Telegram 환경변수를 제거한 뒤 실행한다. 법제처 정식 API 인증과 승인된 WARP
연결은 별도로 준비하며, 인증값을 명령행·보고서에 넣지 않는다. 이 명령은 아직
실행하지 않았다. `crawler_runner.py`는 `.env`를 자동 로드하지 않는다.

```powershell
@'
import os
from pathlib import Path
import runpy
import sys

for key in ("AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY", "AWS_SESSION_TOKEN",
            "R2_BUCKET", "CF_ACCOUNT_ID", "TELEGRAM_BOT_TOKEN", "TELEGRAM_CHAT_ID"):
    os.environ.pop(key, None)
sys.path.insert(0, str(Path("pipeline").resolve()))
sys.argv = ["crawler_runner.py", "--full-bootstrap", "--data-dir",
            "audit/recovery-20261017/candidate"]
runpy.run_path("pipeline/crawler_runner.py", run_name="__main__")
'@ | .venv/Scripts/python.exe -
```

로컬 raw/gzip/manifest 생성까지 허용하고 R2 업로드·운영 state 교체·알림 전송은
허용하지 않는다. 실패하면 같은 candidate 경로와 full-bootstrap mode로 재개한다.
실행 간 원본·candidate·backlog를 덮어 복구 진행 상황을 잃지 않는다.

한 범위의 모든 페이지에서 totalCnt·개별 건수·ID 유일성·날짜 범위·스키마가
확인돼야 upsert한다. 중간 실패는 전량 폐기하고 범위가 backlog에 남아야 한다.
API의 0건은 오류와 구분하되, baseline에 해당 기간 레코드가 있는 경우 별도
대조 대상으로 기록한다. 단순히 총 건수가 10만 이상이라는 이유로 승인하지 않는다.

연 범위가 1,000페이지 상한을 넘거나 totalCnt가 변하면 해당 범위를 실패로
유지한다. 상한 확대나 부분 게시로 우회하지 않는다. 월 범위 분할이 필요한 경우
부모 범위와 모든 자식 범위의 완료를 추적하는 별도 변경을 검토한 뒤 재개한다.

## 3단계 원문 ID와 필드 대조

수집 기간별로 요청 인자(인증값 제외), 실행 시각, 페이지, totalCnt, 실제 건수,
ID 목록과 원문 응답 해시를 별도 감사 자료에 남긴다. 현재 일반 runner의
pipeline-report는 집계만 제공하므로 이것만으로 전수 대조 증거를 대신하지 않는다.
실제 재수집 전 이 수집 증거를 보존할 격리 실행 계측을 추가 검토한다.

대조 결과는 다음 범주별 ID·근거·처리를 담은 표로 만든다.

| 비교 | 통과 조건 |
| --- | --- |
| 원천 → candidate master | 지원 범위의 모든 ID 존재; 제외는 blacklist 등 명시된 사유별 집계와 목록 필요 |
| candidate master → export | 변환 가능한 레코드가 전부 존재; export skip은 원인별 검토, 설명 없는 skip 0 |
| baseline → candidate | 기존 ID·키 삭제 0; 필드 변경·동일 ID의 사건번호 변경은 개별 검토 |
| 키 충돌 | 같은 key의 서로 다른 ID를 모두 유지; 614579처럼 key 존재만으로 완료 판정 금지 |
| 법원·날짜 | 출처의 명시값과 일치; 법원 별칭 자동 합치기 금지; 날짜는 실제 달력 날짜 |
| 예외 표본 | 위 6개 ID 모두 master와 export에 존재; 206264는 16Do10912 / 대법원 / 20181101 |
| 재현성 | 같은 동결 입력과 동일 버전으로 재생성했을 때 raw/gzip/manifest 일치 |

다른 출처나 법원 접두사 변형 때문에 실패하면 해당 범위를 유지한 채 원문을
검토한다. 수집 범위를 몰래 줄이거나 모든 문자를 제거해 사건번호를 만들지 않는다.
원천에서 사라진 기존 레코드도 자동 삭제하지 않고 별도 표로 보고한다.

## 4단계 게시 전 보고와 승인 경계

다음 항목을 사용자에게 보고한 뒤 게시 여부를 검토한다.

- 기준·후보 generation, 코드 commit, 원천 확인 기간, API 호출·재시도 수와 소요 시간
- 키·레코드·법원 수, ID 추가·삭제·변경, 충돌과 제외·미해결 범위별 목록
- 위 6건의 복구 결과와 전체 계획·backlog·원천 대조 완료 범위
- raw/gzip 크기·SHA, 전수 schema·hash·version·total 검증, canonical 4글자 목록 파생 결과
- 전체 lint·Python·Jest·extraction·Store ZIP E2E 결과와 실패·미실행 항목
- 후보 snapshot 전환·오프라인·중간 설치 실패에서 이전 LKG 유지 검증

설명 없는 누락·삭제·충돌, 불완전 범위, 원천 표본 검증 실패가 하나라도 남으면
운영 DB·manifest·state pointer·번들 DB를 갱신하지 않는다.

승인 이후 게시도 immutable object → manifest commit → legacy mirror의 기존
계약을 사용한다. state generation과 공개 artifact의 대응을 확인하고, 클라이언트의
다운그레이드 차단을 유지한다. 게시 후 문제 시 낮은 version을 강제하지 말고
기존 정상 내용을 복구한 더 높은 version의 snapshot을 검증해 배포한다.
현재 사용 중인 정상 snapshot은 새 후보 설치가 끝날 때까지 보존한다.

### 전체 재수집 전에 남은 응답 형식 검토

비블랙리스트 34행은 현재의 좁은 정규화로 처리되지 않고 ID도 배포본에 없다.
blacklist에 들어 있는 형식 오류 5행을 포함하면 parser 실패는 총 39행이다.
이들은 기존 정책상 범위 전체를 실패시키므로 현재 코드만으로 모든 과거 범위의
재수집이 완료된다고 가정해서는 안 된다.

- 법원 약칭과 두 자리 연도: `서울고법-94-구-23625`, `수원고법-2023-누-10668`
- 법원·지원 사이 공백: `부산지방법원 동부지원-2023-가단-130868`
- 법원명과 사건번호 붙여쓰기: `서울고등법원2022나2044416`
- 사건번호 뒤의 사건명 부가: `수원지방법원성남지원-2023-가합-402000 사해행위취소`
- 병합 번호: `2019구합77422, 77439(병합), ...`
- 독립 사건번호는 있으나 법원명이 비어 있어 복원 근거가 없는 경우

복구 전 별도 변경에서는 이 실제 응답을 회귀 fixture로 추가하고, 법원 약칭의
공식 대응 근거와 단일 사건번호의 엄격한 허용 형식을 검토한다. 병합 번호는
문자열을 단순히 쉼표에서 잘라 버리지 말고, 한 원문 ID에 여러 사건번호를
연결하는 저장·내보내기·충돌·canonical 파생 계약부터 검토한다. blacklist
제외 정책과 parser 실패의 관계도 별도 검토하며, 오류를 조용히 skip하지 않는다.

추가 점검에서는 제품 코드·운영 DB·번들 DB·canonical 목록을 변경하지 않았다.
원천별 업로드 시각이 없어 각 누락의 최초 발생 시점이나 직전 게시 후 신규
등록 여부는 확정할 수 없다.

근거 자료는 `audit/2026-10-17/additional-gaps/summary.json`, `results.json`,
`review-list.csv`와 기간별 원본 XML이다. CSV는 기존 ID가 확인된 행을 제외한
검토 목록이며, blacklist·중복 후보·상세 미확인도 분리해 표시한다.
