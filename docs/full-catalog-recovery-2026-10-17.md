2. **Phase 1 — 로컬 완료:** 검증된 378 ID만 추가, 기존 레코드·법원 코드 보존,

   후보를 폐기하면 이번 로컬 변경을 되돌릴 수 있고 운영에는 영향이 없다.
3. **Phase 2 — 미완료, M/L:** conflicts의 29+28행은 상세 원문과 실제 판결 표제로
   번호·법원·날짜를 교차 확인한다. 898행은 양쪽 원문을 비교해 동일 판결 여부를
   판정한다. 29,180행은 상세/원문에서 선고일을 증명할 수 있는 복구 경로를
   소규모로 검증한 후 확대한다. 원천 오류는 임의 정정하지 않고 기록한다.
4. **Phase 3 — 운영 게시 전 별도 검토:** 운영 master와 이 추가분을 serial 기준으로
   대조·가산하고 완전한 기존 state/backlog와 합친다. 현재 운영본이 기준선 이후
   바뀌었다면 새 기준으로 가산 검증한다. unresolved 사유의 처리·사용자 검토,
   전체 release gate 및 이전 cold 설치 실패 해소, 새 immutable payload와 state의
   검증이 선행조건이다. pointer 전환 실패 시 기존 generation을 유지한다.

현재 로컬 후보의 게시 상태는 `publishBlocked=true`다. 운영 master의 새 generation,
R2 업로드, current pointer 전환, 배포 ZIP 갱신은 수행하지 않았다. 기존 기록 삭제,
빈 날짜의 0/오늘 날짜 치환, 약칭의 포괄 치환, 긴 병합의 부분 저장, 검증 pass 제거,
무제한 동시 요청, retry 확대에 의한 시험 통과 처리는 변경 비권고다.

검증 결과다. 이번 실행의 새로운 결과는 데이터 전수 검증 및 실제 전체 후보
설치·387키 조회이며, 전체 최적화 의뢰의 성능 시험·릴리스 완료 선언은 아니다.
