# 수집 재실행 실패 원인과 수정 (2026-10-21)

## 확인된 원인

법제처의 서버 장애로 단정할 근거는 없다. run `39435908498`에서는 같은
runner의 직접/WARP 연결과 실제 최신 선고 조회가 성공했다. 그 뒤 수집이
로컬 원문·서빙 정책 경계에서 중단됐다.

1. `MasterDB.upsert_raw()`가 격리 ID라는 이유만으로 원문 변경 오류를 냈다.
   보관 원문의 고정 해시와 새 원문을 비교하지 않아 동일 재수집도 실패했다.
2. 원문을 유지하고 정정본으로 서빙하는 복구 행에도 같은 문제가 있었다.
   원문/정정본의 관계를 재검증해 쓰기 없이 재사용하는 경로가 필요했다.
3. 원천의 명시적 `대법원2026두31124` 표기를 지원하지 않았다. 법원 약칭을
   추정하거나 병합 목록의 일부만 취하는 처리는 추가하지 않았다.
4. 헌재의 종국일자 `0`을 잘못된 달력 날짜로 처리했다. 기존 저장·압축·기간
   커버리지 정책의 미상 sentinel로 원문 그대로 보존하고, 기존 정상 날짜를
   미상 값으로 덮지 않는다. 다른 잘못된 날짜는 계속 실패한다.
5. 보관 DB와 API 목록의 날짜 표시 형식이 다를 수 있다. 달력 검증을 통과한
   같은 날짜에만 형식 동등성을 허용하며 원문의 날짜 문자열은 바꾸지 않는다.

## 무결성 경계

- 수집 시작 시 검증한 격리 inventory를 읽기 전용 재수집 검사기로 사용한다.
  대상 행은 매번 다시 읽어 일곱 원문 열의 고정 해시를 확인한다.
- ID·사건명·사건번호·법원은 완전히 같아야 한다. 날짜만 검증된 달력 날짜의
  표시 형식 차이를 허용한다. 실제 변경은 기존 오류와 durable backlog를 유지한다.
- 동일한 역사적 격리 원문은 현행 파서가 해석하지 못해도 격리를 유지한 채
  무변경 처리한다. 신규 행에는 이 예외가 없고, 페이지 count·중복 ID·범위·
  최종 export inventory/해시·reference 보존·부분 게시 차단은 그대로 검사한다.
- 검토된 복구 행은 저장 원문과 provenance를 다시 대조한다. 같은 원문 또는
  그 원문에 정확히 결합된 정정본의 재수집만 쓰기 없이 처리한다.
- 격리 해제, 원문 삭제/교체, 신규 오류 자동 격리, 법원 약칭 추정, 병합 번호
  일부 삭제, public 계약 변경, 전송 경로 fallback은 추가하지 않았다.
- API 상세 링크에는 OC 식별자가 포함될 수 있다. 내부 비교용 원문 receipt에는
  다섯 데이터 필드만 담고 URL·링크·응답 본문은 넣지 않는다.

## 추가 게시 전 점검: 원문에 근거한 1건의 날짜 정정

첫 수정 run `39524320885`는 새 데이터 점검 중 직접 중단했다. 기존 실패 run이
비공개 state에 추가한 `613735`의 원천 메타데이터가 미래 날짜 `2026.12.11`이었다.
법제처의 정확한 공개 referral을 따라간 국세청 원출처도 메타데이터는 같았지만,
첨부 판결문 HTML의 **판결선고는 `2025.12.11`**, 사건번호는 `2025두34754`였다.
원문 확인 없이 연도를 바꾸거나 행을 제외하지 않는다.

`source-corrections.json`은 이 건의 원본 목록 7개 필드, 정확한 국세청 URL,
판결문 전체 HTML SHA-256, 정정본 5개 필드를 고정한다. 수집 시 실제 정부 referral과
읽기 전용 NTS 조회 응답을 다시 확인하고, 원본 metadata와 판결문 해시가 모두
일치해야 한다. 임의 redirect·HTTP·외부 host·인증서 검증 해제는 허용하지 않는다.
JSON은 기존 API와 같은 5 MiB 상한으로 읽는다. 동적인 직원·관리 필드를 정정 근거로
쓰거나 로그·fixture에 복사하지 않는다.

원본 `cases.date=20261211`은 그대로 두고, 검토된 recovery overlay와 별도 receipt로
`20251211`을 서빙한다. export 때 원문·정정본·registry 항목 해시·원본 목록 해시를
다시 대조한다. 원본/판결문 변경, receipt 변조, 또는 검토되지 않은 다른 미래 날짜는
계속 게시를 차단한다. 기존 산업재해 known-error registry는 변경하지 않아 과거
receipt의 registry SHA를 무효화하지 않는다.

복사본에서 실제 현재 목록·공식 판결문을 재조회한 결과 원문 날짜는 `20261211`,
서빙 날짜는 `251211`, 출력은 161,081키였으며 기존 격리 49,662행은 그대로였다.
원시 기록은 `live-source-correction.json`에 있다. 운영 반영 성공 여부는 후속 전체
workflow와 게시 후 검증 결과로 확인한다.

첫 수정 CI의 Python job은 코드 테스트에 도달하기 전에 새로 공개된 certifi
인증서 취약점으로 중단됐다. 보안 검사를 우회하지 않고 공식 `2026.10.19` wheel의
검토된 SHA-256으로 운영 lock을 갱신한다. 이 취약점이 과거 연결 오류의 원인이었다는
증거는 없다.
