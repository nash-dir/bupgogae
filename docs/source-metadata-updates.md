# 원천 메타데이터 갱신과 게시 검사

정상 수집값이 과거 공개 레코드의 모든 필드와 같아야 한다는 조건 때문에
2026-11-02·03 수집은 완료 후 게시가 차단됐다. 같은 사건의 법원 정보가
구체화돼도 전체 snapshot이 멈추는 조건이었다.

## 실제 원문 확인

2026-11-05 법제처 공개 판례 페이지의 표제를 확인했다.

| 공개 일련번호 | 사건번호 | 원문 표제의 법원·날짜 | 기존 공개 법원 |
| --- | --- | --- | --- |
| [197717](https://www.law.go.kr/precInfoP.do?precSeq=197717) | 2014나1084 | 광주고등법원(전주), 2015.9.10. | 광주고등법원 |
| [208459](https://www.law.go.kr/precInfoP.do?precSeq=208459) | 2019라508 | 광주고법(제주), 2019.6.24. | 광주고등법원 |

재수집된 전주·제주재판부 정보는 원문과 일치한다. 일련번호·사건번호·날짜·사건명은
그대로이며 법원 코드만 13에서 각각 158·163으로 달라졌다. 개별 번호 예외를 추가하지 않고
일반 갱신 정책을 수정한다.

## 유지하는 조건

- 기존 사건번호 키마다 같은 공개 일련번호와 구성원 수를 유지한다. 다른 키에 같은
  일련번호가 남아 있어도 원래 키가 빠지면 실패한다. 병합 사건의 구성원도 같다.
- 기존 법원명에 할당된 코드의 의미를 바꾸지 않는다. 원천이 더 구체적인 법원명을
  제공하면 그 이름의 코드를 사용한다.
- 수집 파서의 형식·날짜·범위 검사, 전체 payload 스키마·건수·해시 검사,
  known/source/historical correction의 근거·영수증과 격리 원본 검사를 유지한다.
- 비공개 저장 DB와 실제 게시 snapshot을 대조하는 readback의 완전 일치 검사는 유지한다.

## 제거한 조건

- 일반 레코드의 사건명·선고일·법원이 과거 기준값과 완전히 같아야 한다는 조건.
- 새로 수집한 일반 사건명을 과거 제목으로 되돌리던 reference title overlay.
  기존 audit table은 이전 migration과의 호환을 위해 보존하지만 export에는 적용하지 않는다.

export는 기준 구성원의 순서를 유지하면서 현재 메타데이터를 내보낸다.
진단 보고서의 `differenceCount`는 과거 값과의 차이를 보여주는 정보이며,
그 차이만으로 게시 실패를 뜻하지 않는다. 실제 차단 여부는 `exportError`로 확인한다.

## 수집 시작 전의 별도 연결 장애

11월 4일에는 WARP 경유 법제처 연결이 시작 단계에서 실패했다.
[동일 runner 경로 비교](https://github.com/nash-dir/bupgogae/actions/runs/41945923214)에서
원격 DNS의 `socks5h` API 요청은 connect timeout, 로컬 DNS의 `socks5` API 요청은
HTTP 200이었다. 두 경로 모두 WARP 프록시를 사용한다.

하지만 [후속 운영 실행](https://github.com/nash-dir/bupgogae/actions/runs/41948621966)에서는
로컬 DNS 경로도 `socks_04`로 첫 요청부터 실패했다. Cloudflare trace의 WARP 연결 확인은
법제처 API 도달성까지 보장하지 않는다. 한 번의 성공을 근거로 특정 WARP 경로를
항상 강제하는 것은 갱신 경로를 불필요하게 막는다.

daily는 API key 없이 직접 HTTPS API 도달성을 먼저 확인한다. HTTP 200이면 직접 수집하며
WARP 설치·등록은 생략한다. 직접 경로가 실패할 때만 기존 해시 고정 WARP를 준비하고,
로컬 DNS·원격 DNS 순서로 법제처 HTTPS API를 확인해 성공한 경로를 선택한다.
모두 실패하면 수집을 시작하지 않고 재개 state를 보존한다. 약관 확인은 WARP 설치 전에
유지하며 직접 수집이나 state 다운로드에는 WARP 설정을 요구하지 않는다.

선택은 credential 주입 전에 한 번만 하며 수집 중 경로를 바꾸지 않는다.
수집 세션도 환경 proxy·netrc를 무시해 진단과 같은 경로를 사용한다.
무키 HTTP 200은 연결성 확인일 뿐이며 실제 XML·인증·건수·날짜 검사는 수집기가 담당한다.
API 외 R2·GitHub·알림 경로와 TLS 검증은 바꾸지 않는다.

## 기존 병합 판례의 표시 형식

11월 2일에는 [614467](https://www.law.go.kr/precInfoP.do?precSeq=614467)도 보류됐다.
실제 목록 API는 `2018고합5`와 `대전지방법원서산지원`을 반환하고, 상세 API·원문은
`2018고합5, 21(병합), 66(병합), 2019초기65`와 `대전지방법원 서산지원`을 반환한다.
이미 검토·저장한 네 구성원과 같지만 공백과 축약 표시를 문자열 불일치로 거부했다.

기존 검토된 identity를 재확인하는 경로에서만 목록 법원명의 ASCII 공백 차이와
직전 명시된 연도·사건부호를 사용하는 `(병합)` 일련번호 축약을 해석한다.
상세는 저장된 전체 구성원과 순서대로 일치해야 한다. 목록은 전체 또는 이미 허용한
첫 구성원만 인정한다. 누락·변경·모호한 축약, 역할표시 변경은 계속 거부한다.
원본·검토된 값은 재작성하지 않으며 새 사건의 일반 파서나 등록 범위도 넓히지 않는다.

## 일부 조회 실패와 증분 게시

[직접 경로로 수집한 실행](https://github.com/nash-dir/bupgogae/actions/runs/41951611422)은
696개 범위 중 `20260303` 한 범위의 DNS 실패만 남았다. 나머지 범위와 헌재 수집은
완료됐고 건강한 기존 DB에 2행을 추가했지만, backlog 1건 때문에 전체 게시가 차단됐다.

건강한 증분 DB에서는 `request_failed` 조회 실패만 남고 circuit breaker가 없으면
완료 범위를 게시한다. 실패 범위는 전체 페이지가 모이지 않아 upsert되지 않으므로
기존 데이터가 유지된다. backlog도 보존해 다음 실행에서 우선 재시도한다.
report는 `complete` 대신 `incremental_backlog`와 실제 미해결 건수를 기록한다.
초기 전체 구축, 미시도·파싱·식별자 오류, baseline 실패 및 circuit breaker는
계속 게시를 차단한다. export의 구성원 보존·근거·전체 payload 검사는 그대로 유지한다.

## 순환 수집 범위 밖 자료의 즉시 갱신

정규 실행은 모든 과거 선고일을 하루에 다시 읽지 않는다. 원문에서 확인한 변경을
즉시 반영하려면 `Daily Crawler Pipeline` 수동 입력 `refresh_dates`에 쉼표로 구분한
선고일을 지정한다(예: `20150910,20190624`). 지정 선고일과 기존 backlog만 기존 API
파서·범위별 원자 upsert로 수집하며 전체 master를 보존한다. 법원·사건명 등 값을
수동으로 주입하거나 특정 일련번호 예외를 만들지 않는다.

최대 32개 실제 달력 날짜를 받고 중복은 제거한다. 건강한 증분 baseline이 필수이며
full bootstrap·기존 복구 모드와 함께 사용할 수 없다. bootstrap backlog도 대체하지
않는다. 날짜를 비워 두면 정규 순환 수집을 그대로 수행한다. 네트워크 경로 선택,
state 전달·보존, export·게시 검사와 공개 계약은 정규 실행과 동일하다.
